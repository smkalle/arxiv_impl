§2 Revised Scope

What's In and What's Out

In Scope — EpochForge Lite MVP
  • Archive tree (dict in memory, JSON-persisted) with CMP and ε-best-belief scoring
  • Thompson sampling over clade meta-productivity for node selection
  • Two agentic roles in shared workspace: Coder (generates Python solutions) and Reviewer (scores code quality via LLM prompt)
  • Meta-agent that edits the shared workspace codebase (LLM-generated unified diffs)
  • Evaluator role (Reviewer) co-evolves alongside the Coder in the same archive
  • One epoch boundary at checkpoint B=30; selective erasure of reviewer-scored records
  • ε-best-belief evaluator promotion: challenger vs incumbent on HumanEval test suite
  • HumanEval 20-task stratified subset with Python subprocess test execution
  • Blended token counter (input + 5× output) tracking per run
  • HGM-H baseline run (same code, frozen reviewer throughout) for comparison
  • results.json + plot.py for utility trajectory and token cost chart
Out of Scope — Not in Lite
  • Docker container isolation per node
  • SQLite or any relational database
  • Streamlit or any web dashboard
  • CRAVE dataset or any external evaluator ground-truth dataset
  • Adversarial pool and adversarial epoch objectives
  • Specialist vs. generalist agent distinction
  • Multiple evaluator slots (M > 1)
  • Polyglot multi-language benchmark
  • More than one epoch boundary
  • Parallel / distributed search
  • Any model other than gemini-3.5-flash
  • Production API, auth, or multi-user support
⚑

Key design constraint: In the Lite prototype, the Reviewer's "ground truth anchor" for evaluator promotion is the same HumanEval test suite used to score the Coder. A challenger reviewer wins promotion if it better predicts which Coder solutions will pass tests — measured by computing Reviewer acceptance vs. actual test outcome on a 50-sample held-out split. This sidesteps the need for a separate GT dataset like CRAVE.

§3 Cost Model

Budget Breakdown per Run

All estimates use gemini-3.5-flash pricing: $1.50/1M input, $9.00/1M output, $0.15/1M cached input. Blended cost = input cost + 5× output cost (paper's metric). A "run" is one complete RQGM search with B=80 evaluations. Reviewer prompts are cached — same 1,200-token system prompt reused across all 80 calls drops input cost to $0.15/1M for that portion.

◈

Gemini context caching: The reviewer system prompt (~1,200 tokens, same across all 80 calls) is cached via the Gemini API caching endpoint. Cached input tokens cost $0.15/1M vs $1.50/1M uncached — a 10× reduction for that portion. Cache TTL set to 600s (covers one full run). Do not set temperature, top_p, or top_k for Gemini 3.5 Flash — Google recommends defaults only. Use thinking_level="medium" (the default) for the meta-agent; switch to "low" for reviewer/coder calls to reduce latency and output tokens.

§4 Simplified Architecture

Four Files, Flat Structure

No package, no modules, no abstract base classes. Four Python files share a single archive.json state file. All LLM calls go through one thin wrapper in llm.py.

epochforge-lite/ ├── archive.py # Archive tree + Thompson sampling + CMP + ε-best-belief │ # Nodes stored as dicts; persisted to archive.json after each step │ # Also owns: selective_erase(), recompute_clade() │ ├── search.py # Main loop: UCB-Air gate + epoch manager + 3-level sampler │ # Runs the coder, runs the reviewer, calls archive.record() │ # Detects checkpoint B=30 → triggers epoch boundary │ # Epoch boundary: run_promotion_contest() → selective_erase() │ ├── agents.py # MetaAgent: generates code diffs from parent workspace context │ # CoderAgent: generates Python solution for a HumanEval task │ # ReviewerAgent: scores solution (0/1) via LLM prompt │ # All agents use llm.call() — model string is a constant at top │ ├── llm.py # Google GenAI SDK wrapper around gemini-3.5-flash │ # Context cache for reviewer prompt (TTL=600s, $0.15/1M) │ # thinking_level: "medium" for meta-agent, "low" for eval calls │ # Blended token counter (input + 5× output); LRU cache on outputs │ ├── plot.py # Reads results.json → matplotlib chart (utility vs tokens) │ # One chart: RQGM trajectory vs HGM-H baseline │ # Marks epoch boundary with a vertical dashed line │ ├── tasks/ │ └── humaneval_20.json # 20 HumanEval tasks (stratified: easy/medium/hard) │ # Each: {task_id, prompt, test_code, difficulty} │ └── archive.json # Runtime state (auto-created). Gitignored. # {nodes: [...], utility_records: [...], epoch_events: [...]}
◈

Workspace model: Each archive node's "codebase" is just two Python strings — coder_fn and reviewer_fn — stored directly in the node dict. The meta-agent is prompted to return a JSON object with updated versions of either or both. No file system, no git, no diff application. For a 20-task prototype this is sufficient.

llm.py — Google GenAI SDK Wrapper

# llm.py — google-genai SDK wrapper import google.generativeai as genai from functools import lru_cache MODEL = "gemini-3.5-flash" THINKING_META = "medium" # meta-agent: needs reasoning depth THINKING_EVAL = "low" # coder/reviewer: speed > depth # NOTE: do NOT set temperature / top_p / top_k on Gemini 3.5 Flash _token_log = {"input": 0, "output": 0} def call(prompt, system=None, thinking=THINKING_EVAL): model = genai.GenerativeModel( model_name=MODEL, system_instruction=system, generation_config={"thinking_level": thinking} ) resp = model.generate_content(prompt) _token_log["input"] += resp.usage_metadata.prompt_token_count _token_log["output"] += resp.usage_metadata.candidates_token_count return resp.text def blended_tokens(): # paper's metric: input + 5× output return _token_log["input"] + 5 * _token_log["output"] def blended_cost_usd(): # $1.50/1M input, $9.00/1M output (cached input handled separately) return _token_log["input"] / 1e6 * 1.50 + _token_log["output"] / 1e6 * 9.00 # LRU cache on reviewer outputs — same (solution_hash, reviewer_fn_hash) # returns same binary score without an API call. Selective erasure just # re-runs the scoring logic on the cached text, not a new Gemini call. @lru_cache(maxsize=2048) def cached_reviewer_call(solution_hash, reviewer_fn_hash, task_prompt): return call(task_prompt, thinking=THINKING_EVAL)

Core Search Loop (search.py)

# search.py — main loop (simplified) MODEL = "gemini-3.5-flash" THINKING_META = "medium" # meta-agent: needs reasoning for code edits THINKING_EVAL = "low" # coder/reviewer: latency-sensitive, no temp/top_p BUDGET = 80 # total task evaluations CHECKPOINT = 30 # single epoch boundary EPSILON = 0.05 # ε for best-belief scoring ALPHA = 0.6 # UCB-Air expansion exponent TASKS = load_tasks("tasks/humaneval_20.json") def run(mode="rqgm"): # mode="hgm_h" for baseline archive = Archive() epoch = 0 boundary_fired = False for step in range(BUDGET): # 1. Epoch boundary check (single checkpoint) if mode == "rqgm" and step == CHECKPOINT and not boundary_fired: run_epoch_boundary(archive) boundary_fired = True # 2. UCB-Air gate: expand or evaluate if step**ALPHA >= len(archive.nodes): node = archive.thompson_sample() child = MetaAgent().expand(node, archive.ancestor_logs(node)) archive.add_child(node, child) else: # 3. Three-level sample: node → role → task node = archive.thompson_sample() role = least_evaluated_role(node) # "coder" or "reviewer" task = least_evaluated_task(node, role, TASKS) outcome = evaluate(node, role, task, epoch) archive.record(node, role, task, outcome, epoch) archive.save("archive.json") return archive.best_belief_agent(EPSILON)

Epoch Boundary Procedure (in search.py)

def run_epoch_boundary(archive): # 1. Score all reviewer nodes on held-out HumanEval test pass prediction # "Does reviewer accept this solution?" vs "Does test suite pass?" # Accuracy = fraction of 50 held-out solutions where reviewer and tests agree incumbent = archive.get_incumbent_reviewer() challengers = [n for n in archive.nodes if n.role == "reviewer"] scores = {n.id: gt_accuracy(n, HELD_OUT_50) for n in challengers + [incumbent]} # 2. ε-best-belief winner (ties → keep incumbent) winner_id = max(scores, key=lambda k: eps_best_belief(*scores[k], eps=EPSILON)) if winner_id == incumbent.id: log_event("retained"); return # 3. Selective erasure: remove all reviewer-scored records from epoch 0 erased = archive.selective_erase(role="reviewer", epoch=0) archive.set_incumbent_reviewer(winner_id, new_epoch=1) archive.recompute_clade_aggregates() log_event("promoted", records_erased=erased)
§5 Data Model

JSON Schema — archive.json

All state lives in one JSON file. Three top-level arrays. No foreign key constraints — references are by string ID. The entire file is written atomically after each step using a temp-file + rename pattern.

§6 Epoch Protocol

The One Epoch Boundary

With B=80 and a single checkpoint at step 30, there is exactly one opportunity for an evaluator upgrade. The protocol must still be implemented correctly — the correctness guarantee is what the prototype exists to validate.

StepActionInvariant Checked
Steps 0–29 Normal search. Reviewer nodes co-evolve alongside coder nodes. All reviewer records tagged epoch=0. Coder test records tagged is_verifiable=True. All utility_records have epoch=0. CMP is consistent with s_own/f_own.
Step 30 (Boundary) 1. Score all reviewer nodes on held-out 50-sample set.
2. Compute ε-best-belief for each.
3. Promote winner (if != incumbent) or retain.
4. If promoted: delete all role="reviewer", epoch=0 records. Increment epoch to 1. Recompute CMP for all nodes. Log to epoch_events.		 After erasure: zero records exist with role="reviewer" AND epoch=0. All surviving records are either coder (is_verifiable=True) or reviewer epoch=1. Node s_own + f_own match surviving records.
Steps 31–80 Continues under new (or same) reviewer. New reviewer evaluations tagged epoch=1. Coder continues to accumulate test-verified records normally. No records with epoch=0 exist. CMP is consistent.
⚑

Critical test: After every call to selective_erase(), the test suite must assert len([r for r in archive["utility_records"] if r["role"]=="reviewer" and r["epoch"]==0]) == 0. This assertion runs in CI on every commit and after every simulated epoch boundary in the integration test.

Ground-Truth Accuracy — How Reviewer Promotion Works in Lite

Without CRAVE, the reviewer's "ground truth" is whether it correctly predicts coder test outcomes. The 50-sample held-out set is constructed at run start: pick 50 random (task, solution) pairs from the HumanEval training split, run the test suite to get ground-truth pass/fail, store them. A reviewer's GT accuracy = fraction it correctly classifies.

def gt_accuracy(reviewer_node, held_out_50): # held_out_50: list of {solution, task, ground_truth_pass: bool} correct = 0 for item in held_out_50: reviewer_says_pass = ReviewerAgent(reviewer_node).score( item["solution"], item["task"] ) == 1 if reviewer_says_pass == item["ground_truth_pass"]: correct += 1 return (correct, len(held_out_50) - correct) # (successes, failures)

§9 Open Questions

Decisions Before Build Starts

Can Gemini 3.5 Flash write functional Python patches reliably? The meta-agent must produce valid Python that actually changes behavior. Gemini 3.5 Flash is weaker at code generation than Sonnet. We should spike this before committing to Phase 1: prompt Gemini 3.5 Flash to modify a simple Python function 20 times and measure the rate of syntactically valid, meaningfully different outputs. If it's below 50%, we either switch to Sonnet for meta-agent calls only (keeping Gemini 3.5 Flash for evaluation) or simplify the workspace model further.
Should the reviewer be a prompted LLM or a co-evolved code function? In the paper, the reviewer is a full agentic process that evolves its own code. In Lite, the simplest version is a fixed LLM prompt that scores solutions, with the meta-agent only evolving the prompt string rather than full code. This is much cheaper and more stable. Is a prompt-as-evaluator faithful enough to the paper's mechanism, or does it undermine the core claim?
Is 20 HumanEval tasks enough statistical signal? With B=80 evaluations split across 20 tasks and ~25 nodes in the archive, each node gets roughly 3 evaluations on average. ε-best-belief with n=3 is very wide. We may need to either increase the task pool to 40 (doubling cost) or increase B to 160 (doubling cost). Recommend: run a dry cost estimate first with thinking_level="low" on eval calls, then decide. Sampling with replacement is effective here — the reviewer output cache makes repeated (task, node) pairs essentially free after the first API call.
What is the seed node's coder_fn and reviewer_fn? The seed is initialized with a minimal coder (e.g., a template that returns an empty string) and a minimal reviewer (e.g., always returns 1). Alternatively, the seed can be a passable but weak solution generated by Gemini 3.5 Flash at startup. The second approach may produce more interesting search dynamics but adds one extra API call at initialization.
How do we handle the case where no challenger emerges by step 30? If all nodes in the archive are coder-dominant (meta-agent only edits coder_fn), there may be no meaningful challenger reviewers at the checkpoint. The boundary fires but returns "no_challenger." The run then continues as HGM-H for steps 31–80. This is a valid outcome but makes the RQGM run identical to baseline. We need a fallback: either prompt the meta-agent to also evolve reviewer_fn, or initialize the archive with a separate reviewer lineage node at step 0.
