Overview & Goals

Planning Artifact
What this is. A spec-planning document for the KB Ingestor Admin Console — a purpose-built operations and observability dashboard for admins and ops teams managing the kb-ingestor pipeline. This is not a general analytics tool. Every screen serves a pipeline operator, not a business analyst.
Primary goal

Give operators full visibility into every ingestion run — from source file selection through Arrow pipeline stages to FAISS index health — without needing to SSH into a server or read logs manually.

Secondary goal

Enable admins to configure, trigger, and schedule new ingestion runs from a UI — with source mapping, model selection, and batch tuning — without touching the CLI or config files directly.

Non-goal

Not a search interface. Not a ticket viewer. Not a BI tool. The dashboard ends at the pipeline boundary — SIRA query UI is a separate surface owned by the SIRA team.

Design north star. An ops engineer should be able to diagnose a failed ingestion run, identify the failed batch, and trigger a targeted re-run — in under 90 seconds, without leaving the dashboard.

User Personas

2 Personas
A
Admin
Pipeline owner · Full access
Primary
  • Sets up new pipeline configurations — source mapping, embed model, batch params
  • Manages credentials / API tokens for Zendesk and Jira source connectors
  • Schedules recurring ingestion runs (cron or on-demand)
  • Reviews benchmark reports and tunes performance parameters
  • Can delete indexes, purge artifacts, and rotate models
  • Receives alert notifications for pipeline failures
configure schedule tune alert-config
O
Ops / On-call
Incident responder · Read + Retry access
Secondary
  • Monitors live run status and per-stage latency in real time
  • Reads error details for failed batches and downloads failed_rows.json
  • Triggers targeted re-runs on failed batch IDs (cannot change configuration)
  • Views FAISS index health: doc count, last-updated, dim consistency
  • Searches and filters historical run logs by date, source, status
  • No access to credentials, scheduling, or destructive actions

Pipeline Observability Design

Core Pattern
Principle. Observability maps 1:1 to the operator DAG. Every metric, log, and alert is scoped to OP-1 through OP-4. There is no aggregate "pipeline health" metric that obscures which stage failed. Operators are the atomic unit of visibility.
OP-1
Load & Normalize
Metrics: t_load, rows_read, rows_dropped, schema_errors
OP-2
Chunk & Preprocess
Metrics: t_preprocess, chunks_out, chunks_filtered, avg_chunk_len
OP-3
Embed (Async Batch)
Metrics: t_embed, batches_total, batches_failed, worker_utilization
OP-4
FAISS Upsert
Metrics: t_upsert, vectors_added, index_size_mb, dim_check_pass
Stage Key Metric Alert Trigger Displayed As Granularity
OP-1 t_load, rows dropped null_drop_rate > 10% Duration bar + drop count badge Per run
OP-2 chunks filtered, avg chunk len filter_rate > 20% Distribution histogram Per run
OP-3 batch success rate, worker util, t_embed batch_failure or throughput < SLO Batch status grid + sparkline Per batch
OP-4 vectors_added, dim_check, t_upsert dim_mismatch = true Index health indicator Per run
E2E t_total, speedup vs baseline speedup < 2.0× Speedup gauge vs 2.5× target Per run

UX & Design Best Practices

Ops Console Patterns
↯
Real-time updates without full refresh
  • SSEUse Server-Sent Events for live run status — lighter than WebSocket for one-way push
  • POLLFall back to 5-sec polling if SSE unavailable (same API endpoint)
  • DELTASend delta updates only — never re-send the full run object on each tick
  • STALEShow "last updated X seconds ago" badge when connection is interrupted
  • IDLEPause live updates when tab is not visible (Page Visibility API)
⚠
Destructive action guards
  • CONFAll destructive actions (delete index, purge artifacts) require a confirmation modal with typed confirmation string
  • DIFFVisually separate destructive buttons — never in the same button group as safe actions
  • UNDOWhere possible, soft-delete with a 30-second undo window before permanent deletion
  • LOGEvery destructive action is audit-logged with user, timestamp, and target resource
≡
Status communication
  • BADGEUse a fixed 5-state vocabulary: Running · Queued · Done · Failed · Partial — no custom states
  • COLORGreen=done, teal=running, amber=queued/partial, red=failed, gray=idle — consistent everywhere
  • ICONAlways pair color with an icon or shape — never rely on color alone (accessibility)
  • COPYStatus labels use past tense for completed states ("Succeeded", not "Success")
⊘
Error presentation
  • WHEREShow errors at the closest point to failure — batch row, not just run header
  • WHATDisplay error class + human message + actionable next step (not just stack trace)
  • COPYCopy error button copies full stack trace + run ID + timestamp as JSON — for paste into incident ticket
  • LINKEach error class links to its documentation anchor in the spec
⊡
Data tables for ops
  • STICKYSticky header + sticky first column for wide tables (batch inspector)
  • SORTDefault sort: newest first. Always show sort direction in header
  • FILTERFilter by status, date range, and source — filters persist across navigation via URL params
  • DENSITYOffer compact / default density toggle — ops users often prefer compact
  • EXPORTCSV export for all tables — ops needs to paste into incident reports
⌛
Loading & empty states
  • SKELUse skeleton screens matching the actual layout — never spinners for predictable data shapes
  • 300Show skeleton only after 300ms delay — avoids flash for fast loads
  • EMPTYEmpty run history: show onboarding CTA ("No ingestion runs yet — trigger your first run") not a blank table
  • ZEROZero-state index health page: show expected artifact paths even when no index exists yet

Do / Don't — Ops Console Patterns

Anti-patterns
Do
  • Show per-stage timings on every run — make it trivial to see which OP is slow
  • Keep the 90-second ops recovery path as the primary interaction model
  • Surface speedup vs baseline on every run — makes the Arrow value prop visible over time
  • Use URL-based state for filters and drill-down — ops needs deep links for incident handoffs
  • Show batch count and failed batch count on the run summary row
  • Disable the retry button with clear reason text if a run is still active
  • Make "copy run ID" a one-click action — it's pasted into incident tickets constantly
  • Persist last-used config in the New Ingestion wizard — repeat runs are 90% the same
Don't
  • Don't aggregate OP timings into a single "pipeline health" score — it hides the actual bottleneck
  • Don't auto-navigate after triggering a run — ops wants to see the live progress on the same screen
  • Don't use a modal for the New Ingestion wizard — it's a 5-step flow, it deserves a full page
  • Don't show stack traces by default — show them in a collapsible or "details" panel
  • Don't use toast for run completion on long runs — use an in-page status update
  • Don't give ops users access to model or credential config — separate role permissions clearly
  • Don't paginate the batch table inside a run — ops needs to scan all 24 batches at once
  • Don't use color alone for failed batch status — use an icon + color + text label

API / Data Contracts

Backend Interface
Design choice. The admin dashboard is a thin React frontend calling a FastAPI backend that wraps the kb-ingestor Python API. The dashboard never directly reads Arrow IPC or FAISS files — it reads structured JSON from the backend. All artifact downloads go through signed URL endpoints.
Endpoint Method Description Auth Real-time?
/runs GET Paginated run history, filterable by status / date / source Any role —
/runs/{id} GET Full run detail: stage timings, batch table, error details Any role —
/runs/{id}/stream SSE Live stage progress + batch status deltas for active run Any role SSE
/runs POST Trigger new ingestion run with IngestConfig payload Admin —
/runs/{id}/retry POST Retry failed batches only; body: { "batch_ids": [...] } Admin, Ops —
/runs/{id}/validate POST Pre-flight schema validation without embedding Admin —
/indexes GET Index registry: name, doc count, dim, last updated, size Any role —
/indexes/{name}/artifacts GET Returns signed download URLs for .arrow, .faiss, run_summary.json Admin, Ops —
/configs GET / POST Saved pipeline configurations CRUD Admin (write), All (read) —
/schedules GET / POST Cron schedule management (v0.2) Admin —

Build Roadmap

Phased
v0.1 · Week 1–2 alongside kb-ingestor CLI
Foundation — Run Visibility
FastAPI backend wrapping kb-ingestor Python API. Run history table + run detail page with stage timings and batch table. SSE live progress for active runs. Basic auth (admin / ops roles). KPI strip on home screen. Index health page with artifact download.
v0.1.1 · Week 3
Ops Recovery Path
Retry failed batches from the UI. Error detail panel with copy-JSON. Batch status grid. Speedup gauge with SLO target line. URL-based filter state for deep-linking from incident tickets.
v0.2 · Sprint 2
Admin Control Plane
New Ingestion Wizard (5-step, full page). Saved configuration management. Pre-flight dry-run / schema validator. Cron scheduler with human-readable preview. Alert rules + Slack/email channel config.
v0.3 · Sprint 3+
Observability Depth
Historical throughput trends (30-day). Benchmark report viewer. Per-model performance comparison across runs. SIRA query latency correlation (P50/P99 KB search vs index freshness). Audit log for all admin actions.
Recommended tech stack. React (Vite) + Tailwind CSS frontend · FastAPI backend · SQLite for run metadata (swap to Postgres at scale) · SSE for live run streaming · No separate real-time infra — FastAPI native StreamingResponse is sufficient for v0.1 traffic.
